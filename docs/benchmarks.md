# Benchmarks

> Generated by `node bench/render.mjs` from `bench/results/latest.json`. Do not edit by hand; re-run `node bench/run.mjs` to reproduce.

## Setup

- Machine: Apple M5 Max, 18 logical CPUs, 36 GB RAM, darwin 27.2.0; Node v24.18.0.
- Engines: gitleaks 8.30.1; semgrep 1.186.0; osv-scanner 2.7.1. Semgrep uses the registry ruleset `p/default`.
- 3 runs per scenario, reported as median (min–max). The "existing workflow" and `code-intel` full scans are **interleaved** run by run, so slow drift (network, thermal) affects both sides alike.
- Load average (1 min) when each repository started: self 2.47, express 3.37, flask 3.41, juice-shop 2.87.

**Caveats, stated plainly.** This is a single developer workstation that was running other work during the measurements (see load averages), so absolute times are indicative and not a guarantee for your machine. `osv-scanner` queries a remote API and its time varies run to run. Peak RSS is the largest single process reported by `/usr/bin/time`, not the sum of the tree. No baseline for an LLM-only review was measured: it is not comparable and is not claimed.

## What is compared

- **Existing workflow**: run `gitleaks dir .`, `semgrep scan --config p/default .` and `osv-scanner scan source -r .` by hand, one after another, over the whole repository.
- **code-intel full**: `code-intel scan --all --no-cache` (quick profile) on the same repository: the same three engines, run concurrently, with normalization.
- **code-intel incremental**: change one source file, run `code-intel scan --no-cache` (changed files only).

Only engines whose output is a pure function of the file contents are cacheable (gitleaks; semgrep with local rules). Dependency scanners depend on a changing vulnerability database and semgrep registry rules change remotely, so they are never cached. With the default configuration the cache therefore saves only the (small) gitleaks time. This is by design, not a measurement shortfall.

"raw" is what each tool prints when run by hand; "code-intel" is the same engine's count through `code-intel` **before** cross-engine merging (so these columns compare like with like). The severity column is **after** normalization: the same secret reported by two engines becomes one finding, so it can be lower than the sum of the columns. Differences between "raw" and "code-intel" come from `exclude` globs such as `dist/` and `vendor/`, which apply to `code-intel` only.

## Defect injection

Planted 6 defects in a copy of the express repository, then ran `code-intel scan` on the change (1.9 s).

| Planted defect                                           | Detected |
| -------------------------------------------------------- | :------: |
| hardcoded AWS access key                                 |   yes    |
| SQL injection via string concatenation                   |   yes    |
| eval of request data                                     |   yes    |
| command injection, destructured require('child_process') |   yes    |
| command injection, inline require('child_process').exec  |  **no**  |
| vulnerable dependency (lodash 4.17.15)                   |   yes    |

**5 of 6 detected.** The misses are limits of the engines' rules, not of the pipeline: raw semgrep reported 4 findings on exactly those files, and 0 of them were missing from the `code-intel` output (none lost); 1 of those 4 is reported as a single merged finding because gitleaks reported the same secret on the same line (credited in `alsoReportedBy`). Semgrep's `p/default` child-process rule matches some call shapes and not others, which is why the two spellings of the same injection are listed separately. A clean report means "these rules found nothing", never "this code is safe".

## Precision (false positives)

Reviewed by: the assistant that built this project, by reading each finding next to its source line; not an independent human review.

Each pattern-based finding (semgrep, gitleaks) on the two well-maintained libraries was read next to its source line and put in one of three buckets. **Real**: the flagged behavior is present and a maintainer would reasonably act on it in this repository. **Accurate but low value**: the pattern is present, but the context makes it unimportant (example or demo applications, behavior that is intentional by design, or one configuration reported several times by sibling rules). **False positive**: the rule's concern does not apply to the flagged code (input already escaped, an object sent instead of HTML, documentation placeholders). Dependency advisories are facts about pinned versions rather than code patterns, so they are not bucketed and reachability was not assessed. Semgrep's default ignores skip `tests/` directories, so tests were not part of the semgrep scope. The judgments are mine and some are borderline; the per-finding evidence is reproducible with `bench/results/latest.json` (`findingList`).

**Across 67 reviewed findings: 5 real (7%), 50 accurate but low value (75%), 12 false positive (18%).** Read this as: on well-maintained libraries scanned across the whole repository, most pattern findings sit in example code or reflect intentional design, and the tool's value there is the small actionable fraction plus the dependency advisories. This is why the default scope is the files you changed, why SAST findings on untouched lines are hidden, and why the same secret reported by two engines is merged. The sample is small (two repositories) and the judgments are mine.

## What is not measured

- Windows and Linux timings (all numbers above are from one macOS machine).
- `code-intel mutate` on the corpus repositories: mutation testing needs each project's dependencies installed and a tests-only test command. Its behavior is covered by integration tests instead (`test/integration/mutate.test.ts`), not by timing claims.
- Comparison with an LLM-only review. No LLM review was run, so no claim is made about detection versus one.
