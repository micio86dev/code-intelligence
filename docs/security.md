# Security model

`code-intel` is meant to be run by developers and by AI agents, often inside repositories they did not write. That shapes the threat model.

## Assumptions

- **The repository under scan is untrusted.** Its files, `.code-intel.json`, `sgconfig.yml` rules and test scripts may be hostile.
- **The user's machine and installed engines are trusted.** We cannot defend against a compromised `semgrep` binary.

## What we do about it

| Risk                                                         | Mitigation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Shell injection through file names, refs or config values    | Every child process is started with an **argv array and `shell: false`**. Tested with `$(...)`, backticks and pipes (`test/unit/exec.test.ts`). File names starting with `-` are prefixed `./`; `mutate` passes `--mutate=<list>` as one argument. `--since` refs starting with `-` are rejected and refs are verified with `git rev-parse --verify`.                                                                                                                                                                                                                                                                                                                                                                                                   |
| Config values becoming engine flags or remote rules          | The config has no free-form argument field. Semgrep configs must be registry ids (`p/…`, `r/…`) or repo-relative paths; **URLs and leading `-` are rejected**. Paths must be repo-relative with no `..`; a baseline path may not point into `.git` or at the config file.                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Regex denial of service from hostile globs                   | Globs are matched by a **linear-time dynamic-programming matcher with no regular expressions** (cost O(tokens × path length) for any input), plus length, `**`, wildcard and brace-expansion caps. An earlier regex-based version was found vulnerable (first by scanning this repository with itself, then again by an independent review that showed wildcard caps only lower the polynomial degree), so it was replaced, not patched. `impact`'s import scan uses horizontal-whitespace-only patterns and skips files over 1 MB.                                                                                                                                                                                                                     |
| Crafted diffs hiding findings from the changed-line filter   | The diff parser recognizes file headers only inside a file's header block and consumes hunk bodies by the exact line counts their `@@` header declares, so an added line like `++ /dev/null` cannot masquerade as a header.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Hostile `.git/config` executing programs                     | `git` runs with `core.fsmonitor=false`, `diff.external=`, `--no-ext-diff --no-textconv`, and **every configured `filter.<name>.clean/smudge/process` overridden with an empty command** (a worktree diff otherwise runs clean filters). Tests prove both a repository `textconv` and a `clean` filter are not executed, and that each _would_ run without these protections. git-lfs users see raw content instead of pointers for LFS-tracked files, which only changes line ranges for binaries.                                                                                                                                                                                                                                                      |
| Writing outside the repository through symlinks              | Every writer (cache, baseline, `init`) goes through `safeWrite`: each path component is `lstat`-checked, the data goes to a fresh temp file and is renamed over the target, so a planted link is replaced, never followed. `init` uses `lstat`, so a dangling link counts as "exists". A symlinked `.code-intel.json` or baseline is refused on read, and parse errors report only line and column, never the file's text.                                                                                                                                                                                                                                                                                                                              |
| Reading outside the repository through a symlinked directory | Each candidate file's real path must stay inside the repository's real root.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Repository-supplied configuration weakening a scan           | A repository can configure a scan to find less (`exclude: ["*"]`, a catch-all `.gitleaks.toml` allowlist, a `.gitleaksignore`, a high `failOn`, a planted baseline). The report always lists non-default repository config and engine-native suppressors in `config.inEffect` (text, JSON and SARIF): including `.gitleaks.toml`, `.gitleaksignore`, `.semgrepignore`, and a **count of inline `gitleaks:allow` / `nosemgrep` comments**. `--ignore-repo-config` discards `.code-intel.json`, `.gitleaks.toml` (it is not even staged into the directory gitleaks scans), `.gitleaksignore` and the baseline. Inline suppression comments and `.semgrepignore` are honored by the engines and cannot be switched off; they are disclosed, not disabled. |
| Leaking secrets through our own output                       | gitleaks runs with `--redact`; findings carry rule id, location and description but **never the matched text**. Semgrep messages and fixes can interpolate the matched text (verified with a capture-group rule), so secrets-category semgrep findings get a fixed message. Fingerprints hash the source line and are one-way. Tests assert a planted key appears in none of text/JSON/SARIF output, stderr, or the cache. Engine failure messages never include stdout.                                                                                                                                                                                                                                                                                |
| Forged or terminal-hijacking report text                     | The text report escapes control characters in file names, rule ids and messages, so a repository cannot forge `Summary:`/`Result:` lines or move the cursor. JSON and SARIF are structured.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Runaway or hanging engines                                   | Per-engine timeout; the whole process group is killed; output is capped at 64 MiB. A timeout is `exit 3`, never a pass.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Absolute local paths in reports                              | Children get a `$PWD` matching their working directory; engine paths are resolved against the root as written and symlink-resolved; anything still outside becomes `<outside-repository>/<name>`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Leftover files                                               | gitleaks input is staged in a temp directory (hard links where possible) removed in a `finally`. `mutate` removes `reports/` and `.stryker-tmp` it created and only accepts regular files inside the repository.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Cache poisoning / stale results                              | The cache lives **outside the repository** (user cache directory), because a cache inside a repository you scan is attacker-controlled (the key is predictable) and cannot be authenticated. The repository's `.code-intel/cache` is never read or written. Entries are still schema-validated; keys cover tool version, the repository's real path, engine identity, config **and the contents of config and local rule files**, and every input file's content hash. Engines backed by changing databases are never cached. Writes are atomic renames and never fail a scan.                                                                                                                                                                          |
| Duplicate findings hiding new ones                           | Identical lines in one file get distinct fingerprints (the n-th copy has its own identity), so a baselined `eval(x)` cannot hide a newly added copy.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

## What leaves your machine

`code-intel` itself makes no network requests. The engines it drives do, as documented by their projects:

| Engine           | Network use                                                                 | Notes                                                                                                    |
| ---------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| gitleaks         | none                                                                        |                                                                                                          |
| semgrep          | downloads rulesets when a config is a registry id (`p/default`)             | We pass `--metrics=off` and `--disable-version-check`. Use repo-local rule files for fully offline scans |
| osv-scanner      | queries the OSV API with the package names and versions from your lockfiles | **No source code is sent.** The tool also has `--offline` modes; we do not expose them yet (see ROADMAP) |
| trivy (fallback) | downloads its vulnerability database on first use and updates               | We pass `--skip-version-check`                                                                           |
| ast-grep         | none                                                                        |                                                                                                          |
| StrykerJS        | none by our invocation                                                      | We enable only the JSON reporter, never the dashboard                                                    |

If your policy forbids sending dependency lists to a third party, do not run the `deps` category (`-e secrets,sast`) or use an engine mode you control.

## What is stored on disk

`.code-intel/baseline.json` (fingerprint hashes, engine, rule id, path) in the repository, only if you run `baseline`; a result cache in your user cache directory (findings without secrets; delete it any time). Nothing else.

## Known limits

- **Fingerprints are one-way but not secret.** They are the first 64 bits of a SHA-256 of rule, path and the normalized source line. A committed baseline lets someone who can guess a low-entropy line (for example a short password assignment) confirm the guess offline. Do not treat a baseline as safe for a secret that was removed from the code but remains in history; rotate it.
- **`impact` trusts a `.codegraph` index found in the repository** (it is read by CodeGraph, a separate tool). A hostile index can make `impact` report the wrong tests, and it is CodeGraph's parser that reads it. Run `codegraph init` yourself, or ignore `method: "codegraph"` for repositories you do not trust.
- **File-system races (TOCTOU).** Symlink checks happen at write time, not atomically with the write. Exploiting this needs another process racing on your working tree.
- **Release supply chain.** CI downloads gitleaks, osv-scanner, trivy and actionlint with SHA-256 hashes pinned in the repository. semgrep (pipx) and ast-grep/codegraph (npm) are installed by exact version without hash pinning. The privileged release job installs none of them; it requires the tag to be on `main` and a green CI run for the exact commit.
- **Symlinked skill directories in user scope** (stow-style) are refused by the skills installer; it does not write through links.
- **A hostile `.semgrepignore`** is honored by semgrep itself and cannot be disabled by `--ignore-repo-config`; it is listed in `config.inEffect`.
- A malicious _engine_ or a malicious Stryker config/test script runs with your privileges; `mutate` executes the project's own test command by design. Do not run `mutate` on code you would not run tests for.
- Findings are only as good as the engines' rules. A clean report means "these checks found nothing", not "this code is safe".
